**Words.** *The canvases* are "Fin Dashboard · new design" and "Fin Admin · new design" ([UI-02]).
*A board* is one canvas frame with its states; *a state* is one value of the board's `state` enum.
*The export* is the Fin design system's team export: its `api/components/<Name>.md` specs, its token
values and its fonts. *The port* is the copy of the design layer on the old product's redesign
branch into fin-next ([G-04]'s exception, [UI-12]). *A pending composition* is a screen part built
only from design-system primitives and tokens because no board or component exists yet ([UI-03]).
*The kit* is the test-build route that renders every component in every state (§10.3).

### 1.3 `vite.config.ts` (console, Fin Admin and verify)

Owned by P0-G's session G3 (§11.1), then by the UI kit lane of the day (S6-12).

```ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import tailwindcss from "@tailwindcss/vite";
import { tanstackRouter } from "@tanstack/router-plugin/vite";

export default defineConfig(({ mode }) => ({
  plugins: [
    tanstackRouter({                       // before react(); option names UNVERIFIED against 1.169.0
      target: "react",
      autoCodeSplitting: true,
      routesDirectory: "./src/client/routes",
      generatedRouteTree: "./src/client/routeTree.gen.ts",
      routeFileIgnorePrefix: "-",          // files starting "-" are components, never routes
    }),
    react(),
    tailwindcss(),
  ],
  define: { __FIN_KIT__: JSON.stringify(mode === "test") },  // the kit route exists only in `--mode test`
  build: {
    outDir: "dist/static",
    assetsDir: "assets",
    assetsInlineLimit: 0,                  // never a data: URL (FW-C05)
    sourcemap: "hidden",                   // moved out of dist/ into the release's map artefact; sourcemaps-staging uploads it (EX-28)
    modulePreload: { polyfill: false },
    target: "baseline-widely-available",
  },
  server: { proxy: { "/api": "http://localhost:8080" } },   // vite dev only (FW-C17)
}));
```

- No `define` carries an environment value: builds are environment-neutral (spec 01 S0-05). What
  differs per environment arrives in `/env.json` at deploy (§2.3).
- `html.cspNonce` is never set (FW-C04). The relaxed development policy exists only in `vite dev`
  on localhost (FW-C17).
- Release builds run `vite build --mode production`; the e2e job builds `--mode test`, which adds the
  kit route and nothing else (S6-16). A release-build check refuses the kit marker (§6.4).

### 1.4 How a page reaches its API

- Every call is relative and same-origin: `fetch("/api/...")` through `api()` (§2.4). No CORS, no
  preflight, cookies sent by default. Nothing in the browser ever calls `api` or `payments` (FW-C08).
- No route of any single-page app sits under `/api`. A request for `/api` with no slash gets the
  app's document (ARCHITECTURE §5.16); a unit test walks each route tree and fails on a path
  starting `/api` (AC-UI-20).
- **Under the fallback** (ARCHITECTURE §5.17, if S-01 fails): only `api()`'s base changes, read from
  `env.json`'s API origin, and calls carry `credentials: "include"`. `@fin/ui`, the frames and the
  screens do not change.

### 1.6 What leaves the browser

Only requests to the page's own origin. Browser errors go through `reportBrowserError` (§2.6) to
`/api/monitoring/envelope`, page-policy reports to `/api/monitoring/csp`, both parsed and scrubbed
again on the server as untrusted input ([SA-42], ARCHITECTURE §10.5). The exceptions are the selfie
document's Sumsub hosts ([SA-26]) and the docs site's API origin for Try it ([AP-10]). A Playwright
fixture fails any test whose page requests another origin (AC-UI-30).

### 2.2 `index.html`

The same shape in each app; `data-app` is `console`, `admin` or `verify`. No inline script, style
attribute, event handler or nonce anywhere (FW-C04, [SA-45]).

```html
<!doctype html>
<html lang="en-GB" data-app="console">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <meta name="color-scheme" content="light dark">
    <meta property="csp-nonce">
    <title>Fin</title>
    <link rel="icon" href="/favicon.svg" type="image/svg+xml">
    <script src="/theme.js"></script>
    <script type="module" src="/src/client/main.tsx"></script>
  </head>
  <body class="fin-shimmer">
    <a class="sr-only focus:not-sr-only" href="#main">Skip to content</a>
    <div id="root">
      <!-- boot:app -->…the frame skeleton, classes only…<!-- /boot:app -->
      <!-- boot:auth -->…the AuthCard skeleton, classes only…<!-- /boot:auth -->
    </div>
  </body>
</html>
```

- `<meta property="csp-nonce">` carries **no** `nonce` attribute, so the UI SDK adopts constructed
  style sheets, which `style-src 'self'` does not block (D1 §9, D3 §7.2; FW-C06).
- `/theme.js` is a classic, render-blocking, same-origin script: allowed by `script-src 'self'`,
  never `async`, `defer` or `type="module"`. Vite leaves it unbundled because it lives in `public/`.
- Vite injects the hashed stylesheet `<link>` and the `modulepreload` links into `<head>`.
- The boot skeletons use Tailwind classes only (a `style` attribute in parsed HTML would violate
  `style-src`), and each app's stylesheet adds `@source "../../index.html";` so Tailwind sees them.
  The blocks between the markers equal `packages/frame/boot/{app,admin,auth}-skeleton.html`
  byte for byte, checked by `ui-check` (S6-26). Verify carries only the auth block; Fin Admin's app
  block is the admin skeleton (no strip).
- CSS chooses which block shows: `html:not([data-boot="auth"]) [data-boot-block="auth"]` and
  `html[data-boot="auth"] [data-boot-block="app"]` are `hidden`. The app block draws the sidebar at
  `--fin-layout-sidebar` or, under `html[data-sidebar="collapsed"]` at 1280px and wider,
  `--fin-layout-sidebar-collapsed`.
- React's first `root.render` replaces the boot block (it clears the container on first mount; a
  test asserts no boot block remains after `data-ready`, AC-UI-08). The skip link is outside `#root`
  so it exists before JavaScript runs; its target `#main` is AppShell's `<main id="main">`.

### 2.3 Boot sequence (`src/client/main.tsx`)

1. Import order: `./styles.css`, then the scrubbing console guard of `@fin/frame/report` (FW-C15's
   browser twin: nothing logs an `Error` object whole), then everything else.
2. Start two requests in parallel: `GET /env.json` and `GET /api/viewer` (spec 02 §14.4). Start
   the matched route's loader data too (FW-C10).
3. `env.json` (rendered at deploy, spec 01 §7.4) is parsed with a Zod schema in
   `packages/frame/src/env/`, the one schema for every app (spec 01 §7.4): `{ environment:
   "development" | "ci" | "staging" | "production", release: string, apiOrigin?: string, docsOrigin:
   string, consoleOrigin: string }`; unknown fields are ignored. If it fails, the frame shows its
   `error` state with "Couldn't load Fin" and Try again; nothing else renders.
4. The viewer answer (spec 02 §14.4) decides the first navigation. On a route of the `app` frame,
   in the console: `401` goes to `/sign-in?next=<path>`; `gate: "factor_step"` to
   `/sign-in/two-factor`; `gate: "protect_account"` to `/welcome/secure`; `currentOrgId: null` with
   memberships whose roles are all unknown to `/no-access`; otherwise the requested route renders. In
   Fin Admin: `state: "signed_out"` goes to `/sign-in`; `"pending"` and `"factor_step"` to
   `/sign-in/factor`; `"ok"` renders the route. On a route of the `auth` frame, `401`
   is the expected answer and nothing redirects; whether a signed-in viewer stays on an `auth` page
   (Invite does; SignIn may not) is that page's rule in spec 02 §15. `next` is kept only when it
   starts with a single `/` and matches the route list (FW-C09).
5. `createRoot(document.getElementById("root")!).render(<RouterProvider router={router} />)`.
6. When the first route has resolved, the root sets `data-ready` on `<body>` (FW-C16); every e2e
   helper waits for it.
7. After the first paint: load `@sentry/react` with `import()` (§2.6), register the `vite:preloadError`
   handler (one reload, guarded by `sessionStorage` key `fin-reloaded` inside try/catch), and start
   watching `Fin-Release` on API answers (§2.4).

### 2.4 The API client (`packages/frame/src/api/`)

One wrapper, `api()`, and the router's loaders; no query library (FW-C08). It is security-relevant
(it re-sends a step-up intent), so S6-24 proposes tier S for `packages/frame/src/api/**`. Until the
register adopts it, `packages/frame` is tier N throughout (ARCHITECTURE §3.1, EXECUTION §1.7).

```ts
export type ApiErrorKind =
  | "problem"              // Fin's RFC 9457 document, with `code`
  | "network"              // fetch rejected, aborted or timed out: "Couldn't reach Fin"
  | "unexpected_response"; // not Fin's JSON: a Cloudflare block, a 502, a 530 or 1033 page

export class ApiError extends Error {
  readonly kind: ApiErrorKind;
  readonly status: number | null;
  readonly code: string | null;       // problem.code
  readonly requestId: string | null;  // problem.request_id or the Request-Id header
}

export function api<C extends AppContract>(
  contract: C,                         // from packages/app-contracts (Zod in and out)
  input: z.input<C["input"]>,
  opts?: { idempotencyKey?: string; signal?: AbortSignal; organization?: string | null },
): Promise<z.output<C["output"]>>;
```

| Concern | Rule |
|---|---|
| Base | `/api` (same origin). Under the fallback, `env.json`'s API origin with `credentials: "include"` |
| Headers on every unsafe method | `X-Fin-App: console` (or `admin`, `verify`); `Content-Type: application/json` when there is a body; never on GET |
| Organisation | Console org-scoped contracts add `Fin-Organization: <current organisation ID>` (spec 02 S2-10) |
| Idempotency | Every create sends `Idempotency-Key` (a fresh UUID per user action, kept across that action's retries); a money send uses spec 04's `tni_` ID ([MO-07]) |
| `403 step_up_required` | Opens the root StepUp modal for the named intent or window; after the proof, re-sends the same request **once**, same body, same `Idempotency-Key`, plus `Fin-Step-Up-Intent` (spec 02 §7.1, §7.5) |
| `403 step_up_invalid` | Shows "That didn't work. Try again." in the modal; never loops |
| `403 second_factor_required` | Opens "Add a second factor first"; with `hold: true`, navigates to `/welcome/secure` |
| `403 factor_step_required` | Navigates to `/sign-in/two-factor` (Fin Admin `/sign-in/factor`) |

### 2.5 Routes, frames and the router

**File-based routes** (`src/client/routes/`), one folder per path. Files starting `-` are never
routes (`routeFileIgnorePrefix`, UNVERIFIED as the option's name in 1.169.0). In each folder:

| File | Holds |
|---|---|
| `index.tsx` (or `<segment>.tsx`) | `createFileRoute(...)({ validateSearch, loaderDeps, loader, pendingComponent, component, staticData })` |
| `-page.tsx` | The page component |
| `-skeleton.tsx` | The route's `pendingComponent`: its real PageHeader and toolbar, then content-shaped skeletons (§5.2) |
| `-api.ts` | The client calls, each one `api(contract, …)` |
| `-copy.ts` | Fixed copy that is not in a component (status sentences, refusal sentences from the inventory) |
| `-<tab>/` or `-<drawer>.tsx` | Tab panels and drawers addressed by search params; a folder whose name starts `-` holds no routes |

**Frames by static data** (S6-01). Every route declares
`staticData: { frame: "app" | "auth" | "bare"; navId: string | null; pageName: string; needs?:
Permission[]; sandboxOnly?: boolean }`, typed by augmenting TanStack Router's `StaticDataRouteOption`
(UNVERIFIED as the interface's name in 1.170.46). `__root.tsx` renders `<FrameSwitch>`, which reads
the deepest match's `staticData.frame` and wraps the outlet in AppFrame, AdminFrame, AuthFrame or
nothing. So lane folders keep EXECUTION's paths (`routes/customers/**`) with no pathless layout
folder.

**Search parameters** (S6-03), each validated with Zod in `validateSearch`:

- `tab`: a tab of a page with tabs (`overview`, `details`, `people`, `documents`, `money`,
  `activity` on a customer). Absent means the first tab.
- `view`: an open drawer or wizard, by a fixed name (`new`, `create`, `invite`, `add`,
  `send-money`, `add-beneficiary`, `simulate-deposit`, `edit-events`, `roll-secret`, `decide`) or a
  record ID (`trf_…`, `evt_…`, `aud_…`, `whd_…`). Opening pushes a history entry; closing calls
  `history.back()` when this tab opened it, else navigates to the URL without `view`.
- `env`: the console's environment, `production` or absent (Sandbox) (S6-09).
- `saved`: a Fin Admin saved view's ID (S6-30). Filters keep their own names (`status`, `q`,
  `from`, `to`, `actor`, `cursor`).
- `loaderDeps` never include `tab` or `view` on a list route, so opening a drawer or switching a tab
  makes no list request (FW-C11; FW-S5 counts the calls).

**`router.ts`**:

```ts
export const router = createRouter({
  routeTree,
  context: { api, env, viewer },
  defaultPreload: "intent",
  defaultPendingMs: 1000,                // FW-C11: the router's defaults, kept
  defaultPendingMinMs: 500,
  defaultViewTransition: false,          // the motion layer is CSS classes (§5)
  scrollRestoration: true,
  scrollToTopSelectors: ["[data-app-shell-main]"],
  defaultPendingComponent: RoutePending,
  defaultErrorComponent: RouteError,
  defaultNotFoundComponent: RouteNotFound,
});
```

Option names are UNVERIFIED against the installed 1.170.46; the lane reads the installed types first.

**Route guards.** A route whose `staticData.needs` the viewer lacks renders RouteNotAllowed ("Your
role ({role}) can't view this page") in its frame; the server refuses regardless ([SA-16], spec 02
§8.7). A `sandboxOnly` route renders RouteNotFound in Production.

**Titles** (S6-07). The frame sets `document.title` from `staticData.pageName`, never from a
record's name: console `"Sandbox · {pageName} · Fin"` in Sandbox and `"{pageName} · Fin"` in
Production; signed-out pages `"{pageName} · Fin"`; Fin Admin `"{pageName} · Fin Admin"`. Verify's
titles are spec 03's.

**Focus on navigation** (S6-17). When the pathname changes and the new route has resolved, focus
moves to the page's `<h1>` (rendered by PageHeader with `tabIndex={-1}`) and the title is announced
once through the polite region. A change of search parameters only (`tab`, `view`, filters) never
moves focus.

**Sign-out** ends with a full document load (`location.assign("/sign-in")`), and a `pageshow` with
`persisted` set re-checks `GET /api/viewer` before anything is shown (FW-C14; FW-S4).

### 2.6 Browser error reporting (`packages/frame/src/report/`)

- `reportBrowserError(error: unknown, ids: Record<string, string>)` is the one seam. `@fin/ui`'s
  `ReportFailures` provider (the port's `lib/failures.ts`) calls it for every action that throws, so
  a throwing Button or a rejecting MenuItem is reported and shows "That didn't work. Try again."
  (AC-UI-29). Context is IDs only; never `console.error(error)`.
- `@sentry/react` loads after the first route, with `tunnel: "/api/monitoring/envelope"`,
  `sendDefaultPii: false`, no replay, no feedback, no console or DOM breadcrumbs, `release` and
  `environment` from `env.json`. Until it loads, reports queue (at most 20, oldest dropped).
- **The DSN is not in the build or in `env.json`** (S6-10): the browser builds a placeholder
  `https://browser@<page host>/0` from `location.host`, and the relay replaces the envelope's DSN with
  the server-held one before forwarding (open item 11).
- `window.onerror` and `unhandledrejection` go through the same seam. The page-policy reports go to
  `/api/monitoring/csp` through `Reporting-Endpoints` in `_headers`; the UI does nothing for them.

### 5.3 Theme before the first paint ([UI-13])

`packages/frame/boot/theme.js` is copied byte for byte to each app's `public/theme.js` (S6-05). It is
a classic script, run before the body is parsed:

```js
(function () {
  var d = document.documentElement;
  var app = d.getAttribute("data-app");                 // "console" | "admin" | "verify"
  function read(k) { try { return window.localStorage.getItem(k); } catch (e) { return null; } }
  var mq = window.matchMedia ? window.matchMedia("(prefers-color-scheme: dark)") : null;
  function apply() {
    var choice = app === "console" ? read("fin-theme") : null;   // Fin Admin and verify follow the system
    if (choice !== "light" && choice !== "dark") choice = "system";
    var dark = choice === "dark" || (choice === "system" && !!mq && mq.matches);
    d.setAttribute("data-theme", dark ? "dark" : "light");       // explicit even for System
    d.setAttribute("data-theme-choice", choice);
    if (app !== "verify") d.setAttribute("data-sidebar", read("fin-sidebar") === "collapsed" ? "collapsed" : "expanded");
  }
  var AUTH = { console: ["/sign-in", "/sign-up", "/verify-email", "/reset-password", "/invite", "/no-access", "/welcome"],
               admin: ["/sign-in"] };
  var p = location.pathname, auth = app === "verify";
  (AUTH[app] || []).forEach(function (x) { if (p === x || p.indexOf(x + "/") === 0) auth = true; });
  d.setAttribute("data-boot", auth ? "auth" : "app");
  apply();
  if (mq && mq.addEventListener) mq.addEventListener("change", apply);
  window.addEventListener("storage", function (e) { if (e.key === "fin-theme" || e.key === "fin-sidebar") apply(); });
})();
```

- `data-theme` is explicit even for System, because the motion layer's dark shimmer keys on
  `[data-theme="dark"]` only.
- Each host remembers its own choice (`localStorage` is per origin). If storage throws (a private
  window, blocked site data), the page renders in the system theme with the sidebar expanded, and
  nothing fails (AC-UI-08).
- `@fin/frame`'s `useTheme()` and `useSidebar()` write the same keys inside try/catch and set the
  same attributes, so a choice applies at once; the `storage` event keeps other tabs in step.
- Fin sets no theme or sidebar cookie ([SA-43]).

### 7.3 Verify (`verify.<zone>`) and the selfie host (`selfie.<zone>`)

Spec 03 owns verify's flow and paths. This spec fixes only what the UI layer needs:

- A link carries its token only in the fragment: `https://verify.<zone>/c#<token>`, `/p#<token>` or
  `/a#<token>`, with no `/test/` paths (the link record carries the mode; spec 03 §2.5, SD3-02,
  [SA-37]). The entry module reads `location.hash` and replaces the history entry with the bare path
  before any other code runs, so the token leaves the address bar and the history, then posts the
  token to `POST /api/link/open`, which sets `__Host-fin-verify.ls` (FW-C21). Every later step is a
  client route under `/c/`, `/p/` or `/a/`; no path ever holds a bearer value.
- Every verify page uses AuthFrame (frame `auth`); `Referrer-Policy: no-referrer`.
- The selfie document is its own entry (`selfie.html`), at `/s`, opened as
  `https://selfie.<zone>/s#<sft id>.<secret>` (no `/test/` path; Sandbox selfies never open it), on
  its own host and deployment. Its entry reads and clears the fragment the same way and posts the
  ticket to `POST /api/selfie/session`, which sets `__Host-fin-selfie.s` (spec 03 §2.6, SD3-03);
  links into and out of it are full document loads (FW-C20). It renders one AuthCard with the WebSDK's container, a status line and
  its done and failed states; it imports `@fin/ui` and `@fin/frame` like any page. Its document
  carries `<html data-app="verify">`, the same nonce-less meta and its own copy of `theme.js`.

## 8. The screens, day by day, mapped to the canvas boards

**How to read these tables.** Each row is one canvas board (state count in brackets), the route or
overlay that draws it, the lane that builds it and its journey spec file, and its states sorted by
when they must work. State names are the boards' own (Appendix A lists every state of every board).

  loading, load failed, empty, no permission, step-up and refusal states, plus every state that

  (Sunday), spec 04 §26 and §27 (Monday), spec 05 §8 (the docs site).

## 9. Accessibility

**The bar:** WCAG 2.2 level AA for every screen in both themes, at 1440 and on phones. The UI SDK
gives behaviour, focus and ARIA, tested upstream with axe, ARIA snapshots and a virtual screen reader,
but its React adapter runs only in Chromium and no real assistive technology is in its matrix (D1 §6).
Fin's own tests carry the rest.

| Area | Rule | Checked by |
|---|---|---|
| Language | `<html lang="en-GB">`; British spelling in copy | `ui-check`; the copy check |
| Landmarks | One `<header>`, one `<nav aria-label="Main">` (the sidebar; the phone sheet reuses it), one `<main id="main">`, a skip link first in the Tab order | The kit (AC-UI-27) |
| Headings | One `<h1>` per page, from PageHeader; sections use `<h2>`; drawers and dialogs are labelled by their titles | The kit; each board's journey |
| Focus visible | The one 2px focus ring, 2px outside (`--fin-focus-width`, `--fin-focus-offset`), on every focusable element in both themes; never removed | The kit's computed styles; screenshots of focused states in H-02 |
| Focus on navigation | §2.5 (S6-17): to the new page's `<h1>` on a pathname change, the title announced once; never on a tab, view or filter change | AC-UI-27 |
| Focus in overlays | The SDK's rules: on open, the first focusable or the title (Drawer `initialFocus`); on close, back to the trigger, else the earlier focus, else the next control (`useReturnFocus` until the SDK covers it) | The kit's drawer and menu cases (AC-UI-14) |
| Keyboard | Every action reachable by keyboard. Tables: one row in the Tab order, ArrowUp and ArrowDown, Home, End, Enter. Menus, selects and comboboxes: the SDK's WAI-ARIA patterns. Toasts: F8 to the newest and back. Escape closes the top overlay only, except a busy drawer | The kit (AC-UI-14 to AC-UI-17) |
| Names | Every control has an accessible name; icon-only buttons carry `label` and a tooltip that is the same text; icons are `aria-hidden` unless titled; the current page `aria-current="page"`; the current step `aria-current="step"` | Unit tests (static markup) and the kit |
| Forms | Native `<label>`; `aria-invalid` on an invalid control; `aria-describedby` naming the error before the helper; a wizard's step moves focus to the first invalid field; an error summary at the top of long forms ("Check the answer marked below.") | Unit tests; the wizard's kit case |
| Live regions | One polite and one assertive region per document, through `announce()`; skeleton regions say "Loading {label}" once; toasts announce, errors assertively; InlineAlert announces only when it appears after an action | The kit |
| Disabled with a reason | A control a role cannot use is drawn disabled but focusable, with the reason as its description and tooltip ("Your role doesn't allow this. Ask someone who can change roles.") ([SA-16]) | The role matrix (§8.2) |

| Colour alone | Statuses carry a word and an icon, never colour alone; the locked Production option carries the lock and its sentence | Unit tests |

### 10.4 The state manifest ([UI-02], ARCHITECTURE §11.4, S6-13)

- **The pin.** At the 08:00 sitting the owner pins a canvas snapshot (EXECUTION P0-1). P0-G runs
  `node packages/frame/tools/pin-canvas.mjs <canvas folder>` once on the owner's machine, which
  writes `packages/frame/canvas-pin.json`: each canvas's title, the snapshot date, the
  `fin-motion.css` hash, and every board with its state names (Appendix A; 614 dashboard states with
  the Prototype's 9, 316 Fin Admin). It names boards and states only, so it is public-safe; the
  folder path is an argument and is never written down. A re-pin is a reviewed pull request.
- **The fragments.** One file per board, `apps/<app>/e2e/states/<Board>.json`, owned by the board's
  lane, seeded from the pin with every state `pending`:

  ```json
  {
    "board": "Customers",
    "canvas": "fin-dashboard",
    "route": "/customers",
    "states": {
      "list":     { "status": "covered", "day": "sun", "spec": "apps/console/e2e/sun/customers.spec.ts", "test": "lists customers" },
      "tooMany":  { "status": "pending", "day": "h02" },
      "pageFailed": { "status": "unreachable", "reason": "..." }
    }
  }
  ```

  Statuses: `covered` (a journey or kit test, named), `covered-unit` (a component test, named),
  `pending`, `unreachable` (with a reason: a browser cannot reach it, for example the passage of
  hours), `superseded` (with the decision ID, for example `[SA-13]`), and `new` (not on the canvas;
  with `uiRequest` and `drawn: false` until the design lane draws it).
- **The check** (`states:check`, a Vitest file in `packages/frame/test/`, so it runs in `pnpm check`):
  fails when a pinned state has no entry, an entry names a state the pin does not have (except `new`),
  a `covered` entry's spec file or test title does not exist, or a must-have state of a past day is
  still `pending`. It prints the pending count per day; PG-03 needs zero.

### 10.6 How the UI keeps CI fast (R10)

- Journeys run on Chromium only per pull request; Firefox and WebKit run the kit, page-policy and
  security specs per pull request and the journeys nightly (S6-22).
- Turborepo's affected-only runs (ARCHITECTURE §11.3) skip an app's e2e when nothing it imports

- Each app is built once per job in `--mode test` and served statically; no dev server starts.
- Shards start at 4, `workers: 1` first, raised until the slowest shard is under about 8 minutes.

### 11.6 Definition of done for a UI pull request

On top of EXECUTION §1.5:

1. The route declares `staticData`, `validateSearch` and a `-skeleton.tsx` pending component, and
   uses the frame's route states for error, not found and not allowed.
2. The board's state-manifest fragment marks the day's must-have states `covered`, naming the test.
3. The journey specs pass with the page-policy and off-origin fixtures; the pull request says what
   `pnpm --filter @fin/<app> e2e` printed.
4. Screenshot baselines for the board's default, loading and error states are added or unchanged.
5. Copy comes from the board or the inventory; every change from them is listed in the pull request,
   and the copy check passes.
6. A pending composition carries its UR number and a `new` manifest entry, and the design lane has it.
7. The pull request names the board and states the design lane mirrors on the canvas ([G-07]).
8. No new dependency; the bundle budgets hold.
